# 1. Context

The current system has seven role enum values, role checks distributed across controllers/services/frontend, incomplete method-security enforcement, unverified tenant/branch scope checks, and direct entity responses. This plan implements RBAC v2 using six canonical roles, a permission catalog, explicit scope evaluation, normalized assignments, DTO boundaries, and a compatibility migration.

The first release is additive. It preserves `users.role`, `users.store_id`, and `users.branch_id` until parity is proven and legacy cleanup is separately approved.

**Affected Modules:**

- `Backend/src/main/java/com/tamdao/configurations` â€” JWT and Spring Security.
- `Backend/src/main/java/com/tamdao/authorization` â€” new authorization domain module.
- `Backend/src/main/java/com/tamdao/controller`, `service`, `repository` â€” permission and scope enforcement.
- `Backend/src/main/resources` â€” Flyway migrations and secure environment configuration.
- `Frontend/src` â€” authorization profile, capability selectors, and route/action guards.
- `Backend/src/test`, `Frontend/src` tests â€” security, migration, and contract coverage.

**Non-Goals:**

- Rewriting sales, inventory, payment, or subscription business rules beyond authorization boundaries.
- Introducing a microservice, external identity provider, or message broker.
- Removing legacy columns/role enum values in the initial release.
- Tenant-created permissions or advanced e-commerce/loyalty features.

# 2. Constraints

**Language:** Java 21, JavaScript/React 19  
**Architecture:** Spring Boot modular monolith + React/Vite SPA  
**Persistence:** MySQL 8/InnoDB, Spring Data JPA  
**Security:** Spring Security, stateless JWT, Redis revocation/cache

**Rules:**

- Never trust client-provided store, branch, user, or resource IDs without scope verification.
- Controllers return DTOs only; never return password hashes, tokens, or entities.
- Flyway owns production authorization schema changes; do not use `ddl-auto=update` for new RBAC tables.
- `/api/v1` is canonical; compatibility aliases are temporary and isolated.
- Use permissions/overrides for exceptions instead of adding roles.
- Secrets and demo passwords come only from environment/secret management.
- Keep unrelated business behavior unchanged.

**Performance Budgets:**

- Warm Redis authorization lookup target: p95 below 10 ms.
- No permission N+1 queries per request.
- Authorization administration lists use page size maximum 100.

# 3. Conventions

- Java classes use `PascalCase`; methods/variables use `camelCase`.
- Permission codes use `<resource>.<action>`; roles use canonical `ROLE_*` codes.
- API JSON uses `camelCase` and the existing `ApiResponse<T>` envelope.
- `401` means unauthenticated; `403` means permission/scope denied.
- Authorization failures and sensitive mutations use structured audit fields and request IDs.
- Tests use JUnit 5/Spring Security test; names describe behavior such as `should_deny_cross_store_order_access`.
- Each implementation task should stay below roughly 200 production LOC, excluding tests/migrations.

# 4. Contracts

## `AuthorizationService`

```text
authorize(actor, permissionCode, resource) -> AuthorizationDecision
  pre: actor is authenticated and permissionCode is active
  post: allowed only when role/override and scope rules pass
  throws: AuthenticationRequiredException, AuthorizationDeniedException, ScopeViolationException

hasPermission(actor, permissionCode) -> boolean
  pre: actor is authenticated
  post: returns false rather than broadening scope when policy data is unavailable
```

## `ScopeResolver`

```text
resolve(actor, requestedScope) -> ResolvedScope
  pre: requested IDs are untrusted hints
  post: scope is derived from active assignments and verified ownership
  throws: ScopeViolationException when requested scope is outside assignment
```

## `AuthorizationSnapshotProvider`

```text
get(userId, authorizationVersion) -> AuthorizationSnapshot
  post: returns effective roles, permissions, and scopes without secrets
  behavior: Redis first, bounded MySQL fallback, fail closed for protected operations

invalidate(userId, newAuthorizationVersion) -> void
  post: old snapshots cannot authorize after mutation commit
```

## `AuthorizationMutationService`

```text
assignRole(request, actor) -> RoleAssignmentResponse
  pre: target role is active and target scope is inside actor scope
  post: active assignment exists and subject authorization version increments

revokeAssignment(assignmentId, actor) -> void
  pre: assignment exists inside actor scope
  post: assignment becomes inactive; history remains; cache is invalidated

upsertOverride(request, actor) -> OverrideResponse
  pre: permission is active, reason is present, and actor can administer scope
  post: bounded grant/deny override is saved with version bump
```

## Shared data structures

```text
AuthorizationPrincipal { userId, email, authorizationVersion, authenticated }
ResolvedScope { type, storeIds, branchIds }
ResourceReference { resourceType, resourceId?, storeId?, branchId?, ownerUserId? }
AuthorizationDecision { allowed, permissionCode, scopeType, scopeId?, reasonCode, authorizationVersion }
AuthorizationProfileResponse { user, roles, capabilities, authorizationVersion }
RoleAssignmentRequest { userId, roleCode, scope, startsAt, endsAt?, reason }
PermissionOverrideRequest { userId, assignmentId?, permissionCode, effect, scope, expiresAt?, reason }
```

# 5. Target Architecture

```text
HTTP request
  -> JWT validator -> AuthorizationPrincipal
  -> AuthorizationSnapshotProvider -> PolicyEvaluator
  -> ScopeResolver -> controller/service
  -> scope-aware repository -> DTO mapper -> audit when required
```

Components:

- Authentication/JWT: validates signature, revocation, subject, and authorization version.
- Authorization catalog/policy: resolves roles, permissions, assignments, overrides, and scope.
- Security adapter: method security, `401/403`, request context, and exception mapping.
- Resource adapters: store/branch predicates in services and repositories.
- DTO/audit boundary: safe serialization and immutable audit evidence.
- Frontend capability store: UX only; never a security boundary.

Decisions: MySQL is the source of truth, Redis is disposable, JWT permissions are server-resolved, and child scope can narrow but never expand a catalog permission.

# 11. Verification Plan

**Unit Tests:**

- Policy evaluator: role bundles, scope narrowing, override precedence, and expiry.
- Assignment mutation: actor scope, self-escalation, duplicate/revoke/reassign.
- JWT validator: claims, revocation, version mismatch, and legacy compatibility.
- DTO serialization: password/token/entity leak prevention.

**Integration Tests:**

- `401/403` endpoint matrix for all canonical roles.
- Cross-store and cross-branch BOLA tests for every ID-based API.
- Flyway seed/backfill idempotence and invalid-data quarantine.
- Redis invalidation after assignment/override mutation.
- Frontend authorization profile, route capability, and centralized `403` behavior.

**Manual / Smoke Tests:**

- Start backend with secrets supplied by environment and demo seed disabled.
- Enable demo seed only with environment passwords; verify missing values fail startup.
- Login as each canonical role and inspect profile capabilities.
- Change a store/branch ID in a request and confirm backend `403`.
- Revoke a permission and verify old snapshots cannot perform the mutation.

**Success Criteria:**

- All automated tests pass.
- Every `/api/v1` endpoint has a permission/scope mapping.
- No sensitive response/log leak is detected.
- Migration parity has no unresolved widening or mismatch.
- Backend/frontend build remains green.

# 12. Rollout Plan

| Phase | Scope | Gate Criteria |
|---|---|---|
| 1 | Local/staging schema and catalog | Flyway rehearsal, backup, seed/backfill report |
| 2 | Shadow authorization | Normalized vs legacy decisions reconciled |
| 3 | Protected endpoint groups | Integration matrix and BOLA tests pass |
| 4 | Frontend capability UX | Profile/route/action contract passes |
| 5 | Stop legacy writes | Parity stable and rollback reviewed |
| 6 | Legacy cleanup | Client inventory complete; separate release approved |

**Rollback:**

- Disable normalized enforcement while preserving additive tables.
- Keep legacy columns/read paths until parity is restored.
- Revoke affected sessions and increment authorization versions after emergency changes.
- Never roll back by deleting audit events or dropping authorization tables.
