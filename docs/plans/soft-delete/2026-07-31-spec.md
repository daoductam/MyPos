# Soft Delete Migration — Spec Document

> **Status**: Draft  
> **Date**: 2026-07-31  
> **Scope**: All JPA entities in the Backend module

---

## 1. Problem Statement

All 11 DELETE API endpoints currently perform **hard delete** (`repository.deleteById()` / `.delete()`), permanently removing records from the database. This causes:

1. **Data integrity violations** — Deleting a `Customer` with existing `Orders` triggers FK constraint errors
2. **Irrecoverable data loss** — Deleted orders, products, employees cannot be recovered
3. **Audit trail destruction** — No way to trace "who deleted what, when" for compliance
4. **Business continuity risk** — In a POS system, historical transaction data (Orders, Refunds, ShiftReports) is critical for accounting and tax compliance

## 2. Solution: Hibernate-Native Soft Delete

Use `@SQLRestriction` (Hibernate 6.x replacement for deprecated `@Where`) + `@SQLDelete` annotations on a shared `BaseEntity` abstract class to convert all deletes from `DELETE FROM` to `UPDATE SET deleted = true`.

### 2.1 Why This Approach

| Approach | Pros | Cons |
|----------|------|------|
| **`@SQLRestriction` + `@SQLDelete` ✅** | Zero repository changes; automatic filtering on ALL queries; Hibernate-native | Cannot use `@Where` (deprecated in Hibernate 6) |
| Manual `WHERE deleted=false` | Full control | Must modify every query in every repository; error-prone |
| Spring Data `@Query` overrides | Flexible per-repo | Massive boilerplate; easy to miss a query |

## 4. Technical Design

### 4.1 `BaseEntity` Abstract Class

```java
package com.tamdao.modal;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.Setter;
import org.hibernate.annotations.SQLDelete;
import org.hibernate.annotations.SQLRestriction;

import java.time.LocalDateTime;

@Getter
@Setter
@MappedSuperclass
@SQLRestriction("deleted = false")
@SQLDelete(sql = "UPDATE ${table} SET deleted = true, deleted_at = NOW() WHERE id = ?")
public abstract class BaseEntity {

    @Column(nullable = false)
    private Boolean deleted = false;

    private LocalDateTime deletedAt;

    private Long deletedBy;
}
```

> **Note on `@SQLDelete`:** Hibernate's `@SQLDelete` requires per-entity SQL because the table name differs. The `BaseEntity` defines the annotation as a marker, but **each concrete entity must override `@SQLDelete`** with the correct table name. This is a Hibernate limitation.

### 4.2 Revised Per-Entity Pattern

Each entity will:
1. `extends BaseEntity`
2. Override `@SQLDelete` with its specific table name
3. Inherit `@SQLRestriction("deleted = false")` automatically

Example for `Product`:
```java
@Entity
@Table(name = "products")
@SQLDelete(sql = "UPDATE products SET deleted = true, deleted_at = NOW() WHERE id = ?")
// @SQLRestriction inherited from BaseEntity
public class Product extends BaseEntity {
    // ... existing fields unchanged
}
```

### 4.3 `deletedBy` Population

The `@SQLDelete` SQL cannot inject the current user ID directly. The `deletedBy` field will be set **in the service layer** before calling `repository.delete()`:

```java
// In service method:
public void deleteProduct(Long id) {
    Product product = productRepository.findById(id)
        .orElseThrow(() -> new BusinessException(...));
    securityUtil.checkAuthority(product);
    
    // Set audit fields before Hibernate triggers @SQLDelete
    product.setDeletedBy(userService.getCurrentUser().getId());
    productRepository.delete(product);
}
```

Hibernate will execute the `@SQLDelete` UPDATE, and JPA will flush the `deletedBy` change in the same transaction.

### 4.4 Database Column Defaults

All existing rows need `deleted = false` as default. This will be handled by:
1. `@Column(nullable = false)` + `private Boolean deleted = false;` (Java default)
2. A Flyway/manual migration script to add the column with `DEFAULT false` to all existing tables

### 4.5 Migration SQL (for existing data)

```sql
-- Add soft delete columns to all entity tables
ALTER TABLE users ADD COLUMN deleted BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE users ADD COLUMN deleted_at TIMESTAMP NULL;
ALTER TABLE users ADD COLUMN deleted_by BIGINT NULL;

ALTER TABLE stores ADD COLUMN deleted BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE stores ADD COLUMN deleted_at TIMESTAMP NULL;
ALTER TABLE stores ADD COLUMN deleted_by BIGINT NULL;

-- ... repeat for all 15 entity tables:
-- branches, products, categories, customer, orders, order_items,
-- inventories, refund, shift_report, subscriptions,
-- subscription_plans, payment_order, password_reset_tokens
```

> If using `spring.jpa.hibernate.ddl-auto=update`, Hibernate will auto-add the columns. For production, use Flyway.

### 5.2 Implementation: Native Queries to Bypass `@SQLRestriction`

Since `@SQLRestriction` filters ALL queries, restore/trash endpoints need `@Query(nativeQuery = true)` to bypass:

```java
// In ProductRepository:
@Query(value = "SELECT * FROM products WHERE deleted = true AND store_id = :storeId", nativeQuery = true)
List<Product> findDeletedByStoreId(@Param("storeId") Long storeId);

@Modifying
@Query(value = "UPDATE products SET deleted = false, deleted_at = NULL, deleted_by = NULL WHERE id = :id", nativeQuery = true)
void restoreById(@Param("id") Long id);
```

### 5.3 Entities WITHOUT Restore API

These entities are deleted but not restorable via API (restore manually in DB if needed):

- `Order` — Orders should never be "restored" from trash; they use status management
- `Refund` — Immutable financial record
- `ShiftReport` — Immutable operational record
- `Inventory` — Operational state, not a document
- `Category` — Simple, recreatable
- `Store` — Critical, requires super admin DB access
- `Subscription` / `SubscriptionPlan` — Managed by payment flow
- `PaymentOrder` — Managed by payment gateway
- `PasswordResetToken` — Ephemeral

## 6. Service Layer Changes

### 6.1 Pattern: Set `deletedBy` before delete

Every service's delete method will follow this pattern:

```java
public void deleteEntity(Long id) {
    Entity entity = repository.findById(id)
        .orElseThrow(() -> new BusinessException(ErrorCode.RESOURCE_NOT_FOUND, "..."));
    
    // Authorization check (existing)
    securityUtil.checkAuthority(entity);
    
    // NEW: Set audit field
    entity.setDeletedBy(userService.getCurrentUser().getId());
    
    // Existing call — now triggers @SQLDelete (UPDATE instead of DELETE)
    repository.delete(entity);
}
```

## 8. Edge Cases & Considerations

### 8.1 Unique Constraints

When a soft-deleted record has a `unique` column (e.g., `User.email`, `Product.sku`), re-creating a record with the same value will fail with a duplicate key error.

**Solution:** Add `deleted` to unique composite indexes:
```sql
-- Replace single-column unique with composite
ALTER TABLE users DROP INDEX UK_email;
ALTER TABLE users ADD UNIQUE INDEX UK_email_deleted (email, deleted);

ALTER TABLE products DROP INDEX UK_sku;
ALTER TABLE products ADD UNIQUE INDEX UK_sku_deleted (sku, deleted);
```

> **Trade-off:** This allows one active + one soft-deleted record with the same email/SKU, but not two soft-deleted records with the same value. For POS use cases this is acceptable — if multiple soft-deleted duplicates are needed, use a `deleted_at` timestamp in the composite index instead.

### 8.2 Cascade Behavior

- `Order.items` has `cascade = CascadeType.ALL` — When an Order is soft-deleted, the `@SQLDelete` only updates the Order row. **OrderItems are NOT automatically soft-deleted.** This is actually desirable: OrderItems remain in DB for audit, and `@SQLRestriction` on Order means they won't surface in queries.
- If cascade soft-delete is needed later, it must be handled in the service layer (loop through children and delete each).

### 8.3 Performance: Index on `deleted` Column

For large tables (orders, products), add an index:
```sql
CREATE INDEX idx_products_deleted ON products(deleted);
CREATE INDEX idx_orders_deleted ON orders(deleted);
CREATE INDEX idx_users_deleted ON users(deleted);
```

### 8.4 `@PrePersist` / `@PreUpdate` Lifecycle Conflicts

Some entities define `createdAt`/`updatedAt` via `@PrePersist`/`@PreUpdate`. The `BaseEntity` does NOT define these (they stay per-entity) to avoid conflicts. In a future refactoring, `createdAt`/`updatedAt` can be consolidated into `BaseEntity`.
