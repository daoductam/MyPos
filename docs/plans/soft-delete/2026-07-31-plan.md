# Implementation Plan: Soft Delete Migration

Spec Source: `docs/plans/soft-delete/2026-07-31-spec.md`
Owner: `Backend Team`
Last Updated: `2026-07-31`
Status: `Draft`

---

# 1. Context

**Problem:**
All 11 DELETE API endpoints perform hard delete (`repository.deleteById()` / `.delete()`), permanently removing records from the MySQL database. This causes FK constraint violations when related data exists (e.g., deleting a Customer who has Orders), irrecoverable data loss of critical business records (Orders, Refunds), and destroys audit trails needed for compliance in a POS system.

**Affected Modules:**
- `modal/` — All 15 JPA entity classes need to extend new `BaseEntity`
- `service/impl/` — All 11 service implementations with delete methods need audit field population
- `repository/` — 4 repositories need native query methods for trash/restore
- `controller/` — 4 controllers need new trash/restore endpoints
- `exception/` — New `ErrorCode` for "already deleted" / "not in trash" scenarios

**Non-Goals:**
- Frontend UI changes (trash page, restore buttons)
- Scheduled auto-purge of soft-deleted records
- Consolidating duplicated `createdAt`/`updatedAt` into `BaseEntity`
- Soft delete for Redis tokens (uses TTL-based expiration)

---

# 2. Constraints

**Language:** `Java 21`
**Framework:** `Spring Boot 3.5+, Hibernate 6.x`
**Architecture:** `Layered (Controller → Service → Repository → Entity)`

**Rules:**
- Do NOT modify unrelated modules
- Do NOT introduce new external dependencies (Hibernate `@SQLRestriction`/`@SQLDelete` are built-in)
- Maintain backward compatibility with existing API contracts — DELETE endpoints return same HTTP status
- `@Where` is DEPRECATED in Hibernate 6.x — use `@SQLRestriction` instead
- `@SQLDelete` requires per-entity annotation (cannot inherit SQL string from `@MappedSuperclass`)

# 4. Contracts

> Define ALL interfaces and data structures BEFORE task specs.

## Data Structure: `BaseEntity`

```
BaseEntity (abstract, @MappedSuperclass) {
  deleted:    Boolean        — default = false, NOT NULL, column "deleted"
  deletedAt:  LocalDateTime  — nullable, column "deleted_at", set by @SQLDelete
  deletedBy:  Long           — nullable, column "deleted_by", set in service layer before delete
}

Annotations:
  @SQLRestriction("deleted = false")  — auto-filter on all JPQL/HQL/Criteria queries
  @SQLDelete — CANNOT be inherited; each entity overrides with its table name
```

## Interface: Trash/Restore Repository Methods (per applicable repository)

```
findDeletedByStoreId(storeId: Long): List<Entity>
  - pre: storeId is not null, corresponds to an existing Store
  - post: returns all soft-deleted records for this store
  - impl: @Query(nativeQuery = true) to bypass @SQLRestriction

restoreById(id: Long): void
  - pre: id exists in DB with deleted=true
  - post: sets deleted=false, deleted_at=null, deleted_by=null
  - impl: @Modifying @Query(nativeQuery = true)
```

## Interface: Trash/Restore Service Methods (per applicable service)

```
getDeletedItems(storeId: Long): List<DTO>
  - pre: current user has admin authority over the store
  - post: returns DTOs of all soft-deleted items for this store
  - throws: BusinessException(UNAUTHORIZED) if no authority

restoreItem(id: Long): void
  - pre: current user has admin authority; item exists and is soft-deleted
  - post: item is restored (deleted=false, deletedAt=null, deletedBy=null)
  - throws: BusinessException(RESOURCE_NOT_FOUND) if item not in trash
  - throws: BusinessException(UNAUTHORIZED) if no authority
```

## New ErrorCode entries

```
ALREADY_DELETED("ALREADY_DELETED", "Tài nguyên đã bị xóa", HttpStatus.GONE)
  — returned when trying to delete a record that is already soft-deleted (edge case)
```

# 5. Target Architecture

**Components:**
- `BaseEntity` — Abstract superclass with soft delete fields + `@SQLRestriction`
- `Entity classes (15)` — Extend `BaseEntity`, override `@SQLDelete` with table-specific SQL
- `Service layer (11)` — Set `deletedBy` audit field before calling `repository.delete()`
- `Repository layer (4)` — Add native query methods for trash listing and restore
- `Controller layer (4)` — Expose `GET /trash` and `PATCH /restore/{id}` endpoints

**Delete Flow:**
```
Controller.delete(id)
  → Service.deleteEntity(id)
    → entity = repository.findById(id)              // @SQLRestriction auto-filters
    → securityUtil.checkAuthority(entity)            // existing auth check
    → entity.setDeletedBy(currentUser.getId())       // NEW: audit trail
    → repository.delete(entity)                      // triggers @SQLDelete
      → Hibernate: UPDATE <table> SET deleted=true, deleted_at=NOW() WHERE id=?
  ← ResponseEntity.noContent()                       // same API response as before
```

**Restore Flow:**
```
Controller.restore(id)
  → Service.restoreItem(id)
    → repository.findDeletedById(id)                 // native query bypasses @SQLRestriction
    → securityUtil.checkStoreAdmin()                  // admin-only
    → repository.restoreById(id)                      // native UPDATE
  ← ResponseEntity.ok(restoredDto)
```

**Trash Flow:**
```
Controller.getTrash(storeId)
  → Service.getDeletedItems(storeId)
    → repository.findDeletedByStoreId(storeId)        // native query
    → map to DTOs
  ← ResponseEntity.ok(List<DTO>)
```

**Key Decisions:**
- `@SQLDelete` is per-entity (not inheritable) — each entity explicitly declares its UPDATE SQL
- `deletedBy` is set in service layer (not in SQL) because `@SQLDelete` cannot inject Spring Security context
- Native queries bypass `@SQLRestriction` — this is the intended Hibernate mechanism for accessing soft-deleted data
- Unique constraints will include `deleted` column to prevent conflicts with soft-deleted records

# 9. Edge Cases

| # | Scenario | Expected Behavior | Handled In |
|---|----------|-------------------|------------|
| 1 | Delete already soft-deleted record | `findById()` returns empty (filtered by `@SQLRestriction`) → 404 Not Found | TASK-003 |
| 2 | Restore a record that is not deleted | Native query finds no record with `deleted=true` → 404 Not Found | TASK-004 |
| 3 | Create User with same email as soft-deleted User | Composite unique constraint allows it | TASK-005 |
| 4 | Create Product with same SKU as soft-deleted Product | Composite unique constraint allows it | TASK-005 |
| 5 | Two soft-deleted records with same email | Second soft-delete would create duplicate in composite index → handle by checking before delete | TASK-005 |
| 6 | Cascade: Delete Order with OrderItems | `@SQLDelete` only updates Order row; OrderItems remain (desired for audit) | TASK-002 |
| 7 | FK reference to soft-deleted parent | Child records (e.g., Order referencing deleted Customer) remain valid — FK still intact, just `deleted=true` | TASK-002 |
| 8 | `PasswordResetToken` soft delete vs hard delete | Soft delete is harmless; expired tokens filtered by `expiryDate` logic in `AuthServiceImpl` | TASK-002 |
| 9 | `deleteById()` without loading entity first | Must change to `delete(entity)` so `deletedBy` is flushed | TASK-003 |
| 10 | Non-admin trying to access trash/restore | Return 403 Forbidden via `@PreAuthorize` | TASK-004 |

**Multi-Tenant / Authorization:**

| # | Scenario | Expected Behavior | Handled In |
|---|----------|-------------------|------------|
| MT-1 | User from Store A tries to view trash of Store B | Reject with 403 Forbidden | TASK-004 |
| MT-2 | User tries to restore item from another store | Reject with 403 Forbidden | TASK-004 |
| MT-3 | Trash listing without store context | Require `storeId` parameter, scoped to authenticated user's store | TASK-004 |

# 10. Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|------------|------------|
| 1 | `@SQLDelete` SQL string with wrong table name | High — silently updates wrong table | Medium | Code review: verify table name matches `@Table(name)` for each entity |
| 2 | `ddl-auto=update` doesn't drop old unique index | Medium — duplicate key errors on create | High | Manually check MySQL schema after migration; drop old indexes if needed |
| 3 | Existing data has no `deleted` column | High — all queries fail | Low | Column added with `DEFAULT false` — existing rows automatically get `false` |
| 4 | `@SQLRestriction` not inherited by subclass | High — queries return deleted records | Low | `@MappedSuperclass` inherits `@SQLRestriction` — verified in Hibernate 6.x docs |
| 5 | Services using `deleteById(id)` skip `deletedBy` flush | Medium — audit trail incomplete | Medium | TASK-003 explicitly converts all `deleteById(id)` to `delete(entity)` |
